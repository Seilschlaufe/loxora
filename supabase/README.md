# База данных Lexora

1. Создайте проект Supabase. В **SQL Editor** выполните весь файл `migrations/202611080001_lexora.sql` один раз. Альтернатива с Supabase CLI: привяжите проект через `supabase link --project-ref ...`, затем `supabase db push`.
2. В **Authentication → Providers → Email** включите вход по электронной почте. В **URL Configuration** укажите Site URL вашего приложения и разрешённые Redirect URLs. Для локальной разработки добавьте `http://localhost:3000`.
3. Запишите URL проекта и публичный `anon`/publishable key в `NEXT_PUBLIC_SUPABASE_URL` и `NEXT_PUBLIC_SUPABASE_ANON_KEY`. Они предназначены для браузера. **Не используйте service_role key**: он обходит RLS.
4. Перезапустите Next.js после изменения `.env.local`. Для настоящего анализа отдельно настройте серверный `OPENAI_API_KEY`.

Миграция предполагает стандартный контракт Supabase `auth.users`, `auth.uid()` и роли `anon`, `authenticated`. Она не создаёт пользователей и не меняет настройки Auth.

## Контракт таблиц

- `documents`: UUID `id`, UUID `owner_id` (по умолчанию текущий пользователь), `title` (1–160 символов), `content` (1–100 000), `language` (`de`, `en`, `es`), `created_at`.
- `vocabulary_entries`: UUID `id`, `owner_id`, необязательный `document_id`, JSON `analysis`, `demo`, `dedupe_key` (1–128 символов), `created_at`. Уникальность `(owner_id,dedupe_key)` защищает от повторного сохранения; разные контексты должны иметь разные ключи. При удалении документа словарь сохраняется, ссылка на источник становится `null`.
- `reading_progress`: ключ `(owner_id,document_id)`, целочисленная позиция прокрутки в пикселях `position` (0–10 000 000), `updated_at`. При удалении документа прогресс удаляется.
- `analysis_cache`: ключ `(owner_id,cache_key)`, ссылка `document_id` на документ, JSON `analysis`, `created_at`. При удалении документа связанный кэш удаляется; поздний результат анализа не может восстановить данные удалённого документа. Ключ — SHA-256 языка, выделения, контекста и версии промпта; сервер проверяет JSON через Zod.
- `user_preferences`: ключ `owner_id`, тема `light`/`dark`/`system`, `font_size` (16–32), `updated_at`.
- `analysis_leases`: краткоживущие блокировки анализа (90 секунд). Клиент может читать и удалять только свои блокировки, а создавать их может только RPC.

Во всех пользовательских таблицах включена RLS. Политики разрешают только операции текущего владельца. Составные внешние ключи не дают сослаться на чужой документ даже при знании UUID. Широкие привилегии Supabase по умолчанию отозваны; `TRUNCATE`, обходящий RLS, запрещён. Анонимная роль не имеет доступа к таблицам и RPC.

`claim_analysis(p_key)` атомарно выдаёт `ok`, `busy` или `limited`. Действует лимит 20 новых запросов за скользящие 60 секунд на пользователя, общий для всех процессов Next.js. Счётчик хранится в закрытой схеме. Неудачные запросы также расходуют попытку; готовый кэш проверяется до вызова RPC. Модельный SDK может безопасно повторить сетевой запрос один раз; это не отдельное действие пользователя.

`delete_my_data()` удаляет все данные текущего пользователя, включая кэш, настройки и блокировки. Для защиты от обхода лимита сохраняются технические отметки последних запросов — только UUID владельца и время, без документов и ответов ИИ. Они действуют до конца 60-секундного окна; устаревшие строки физически очищаются при следующем анализе или удалении данных, а не автоматическим таймером. Аккаунт Supabase Auth остаётся. Для удаления самого аккаунта нужен отдельный административный процесс, он в приложение не включён.

## Проверка изоляции без внешнего Supabase

При установленном Docker:

```sh
bash supabase/test.sh
```

Скрипт запускает закреплённый PostgreSQL 17 в одноразовом контейнере **без сети и открытых портов**, создаёт минимальный тестовый контракт Auth, применяет настоящую миграцию и исполняет SQL-проверки под ролями пользователей. Контейнер удаляется после запуска. Проверяются RLS для чтения/изменения/удаления, подмена владельца, ссылки на чужие документы, кэш, ограничения запросов, блокировки, дубликаты и удаление своих данных без воздействия на чужие.

Это проверка PostgreSQL и политик, а не end-to-end проверка внешнего Supabase Auth, доставки email или синхронизации двух физических устройств. Их необходимо проверить на вашем настроенном проекте.
